# HTML 우선 디자인 방법

새 장표를 디자인할 때 읽는다. 변환 문법은 [html-contract.md](html-contract.md)에 있다.

## 방향을 구체적으로 정한다

HTML에서는 브라우저로 직접 보면서 글자·면·선·이미지의 관계를 조정한다.
처음부터 PPT 패턴 이름을 고르고 모든 내용을 끼워 넣지 않는다.
`design.md`에는 "고급스럽게" 대신 관객·정보·표현 방식을 구체적으로 적는다.

> 경영진의 빠른 판단을 위한 보고. 밝은 종이색 배경과 짙은 글자, 단일 파랑 강조.
> 핵심 수치는 크게, 근거는 같은 축의 비교 차트로 배치한다. 사진은 현장의 증거일 때만 쓴다.
> 표지는 짧은 결론, 본문은 데이터와 해석, 마지막 장은 결정할 항목을 보여준다.

다른 예:

> 제품 제안. 실제 제품 화면을 주인공으로 사용한다. 브랜드색은 화면과 충돌하지 않는 한 곳에 집중한다.
> 문제 장표는 사용 전후를 비교하고, 기능 설명은 화면의 해당 부분과 가까이 둔다.
> 추상적인 AI 이미지나 장식용 기어 아이콘은 근거가 없는 한 추가하지 않는다.

## 장표마다 주장·근거·관계를 정한다

| 항목 | 결정할 내용 |
|---|---|
| 주장 | 관객이 이 장에서 이해해야 할 한 문장 |
| 근거 | 실제 화면, 숫자, 비교, 원리, 사례 중 가장 직접적인 것 |
| 시각적 관계 | 크기 차이, 전후 변화, 순서, 구조, 위치, 선택 중 무엇을 보여줄지 |

그다음 구도를 고른다. 전체 순서는 사용자의 스토리를 따른다.

- **변화:** 같은 기준선의 전후 비교. 바뀐 부분에 색과 라벨을 집중한다.
- **선택:** 같은 기준의 비교표나 병렬 배치. 추천 이유를 가까이 적는다.
- **성과:** 크게 보이는 지표와 근거 차트. 단위·기간·비교 기준을 함께 둔다.
- **제품:** 실제 화면의 핵심 부분을 크게 보여주고 설명을 해당 위치에 연결한다.
- **원리:** 관계가 읽히는 도식. 연결선에는 방향·책임·순서 같은 의미가 있어야 한다.
- **메시지:** 짧고 큰 문장과 충분한 여백. 빈 곳을 장식으로 채울 필요는 없다.

항목이 실제로 동급일 때 카드나 병렬 열을 사용한다. 카드의 개수가 논리를 대신하게 하지 않는다.
설명 방식은 바뀌어도 여백·서체·강조색·이미지 처리는 덱 전체에서 이어지게 한다.

## 에셋을 고르고 만드는 기준

에셋을 넣기 전에 "이것을 보면 어떤 설명이 줄어드는가"를 적는다. 설명할 역할이 없으면 생략한다.
서비스·교육·참여 프로그램이면 먼저 이용자가 받거나 쓰는 것을 찾는다.
선택 순서와 편집형 제작법은 [사용물 중심 에셋](working-artifacts.md)을 따른다.
실행 기획의 수량·비용·역할은 [운영 가능한 제안서](practical-proposals.md)에서 확인한다.

| 에셋 | 만드는 방법 | 편집형 결과 |
|---|---|---|
| 제품 화면 | 실제 사용자 동작에 관련된 부분을 크게 사용. 공개 시 민감 정보를 제거 | 원본 이미지 + 별도 라벨 |
| 안내지·기록지·도구 | 누가 언제 무엇을 읽거나 적는지 정하고 실제 항목을 설계 | native shape + text / table |
| 사진 | 실제 현장·사람·제품의 맥락. 크롭과 색 처리를 통일 | 교체 가능한 이미지 |
| 생성 일러스트 | 실사 자료가 없는 개념 설명에 한정. 재질·빛·시점 유지 | 이미지 + 별도 제목·설명 |
| 관계도 | 단계·책임·흐름을 단색 면·선·독립 텍스트로 설계 | native shape + text |
| 차트 | 주장에 맞는 비교를 선택하고 계산값과 연결 | native chart + 데이터 |
| 표 | 가로로 비교할 기준을 통일하고 중요한 행만 강조 | native table |
| 아이콘 | 구분이 필요한 곳에 동일 계열만 사용 | 지원 도형 또는 로컬 이미지 |

사용 가능한 이미지 생성 도구가 있을 때만 생성한다. 특정 서비스·API 키가 모든 사용자에게 있다고 가정하지 않는다.
원본 이미지가 없으면 편집형 도식이나 타이포그래피로 방향을 정한다.

이미지 프롬프트에는 용도·주제·구도·재질·빛·색 역할·텍스트를 얹을 여백을 명시한다.
예: "운영 개선 제안서의 상황 설명용. 흩어진 문서가 세 묶음으로 정리되는 차분한 종이 오브젝트 일러스트.
같은 높이의 정면 시점, 확산광, 종이색과 짙은 청색. 문서 글자·로고·제목은 넣지 않고 왼쪽 설명 공간을 남긴다."
생성 이미지를 실제 근거로 제시하지 않는다. 실제 화면이 필요한 장표를 가상의 UI로 대체하지 않는다.

에셋은 프로젝트에 저장하고 `assets.json`에 파일·사용 장표·출처·용도·라이선스를 기록한다.
생성 이미지에는 프롬프트도 기록한다. 원격 URL에 의존한 상태로 변환하지 않는다.

## 글자와 여백의 시작값

Studio로 시작할 때는 [시스템의 토큰](studio-system.md)을 우선한다. 아래 범위는 별도 브랜드를 적용할 때의 참고값이다.

1280×720px의 시작값이다. 사용자 템플릿·밀도·언어에 따라 조정한다.

- 외곽 여백 56~72px. 제목·본문·각주의 좌측 기준선을 공유한다.
- 표지 제목 64~88px, 본문 제목 42~52px, 본문 24~30px, 표·보조 설명 20~24px.
- 출처·페이지 14~18px. 핵심 설명을 각주 크기로 줄이지 않는다.
- 한글 제목 줄간격은 대체로 1.2~1.35. 조사·한 글자만 다음 줄에 남으면 문장·폭부터 조정한다.
- 강조색은 의미가 있는 부분에 집중한다. 여러 강조가 같은 강도로 경쟁하지 않게 한다.
- 폰트는 브라우저와 PPT 렌더 환경 모두에서 확인한다. 다른 PC의 폰트 대체 가능성은 별도로 알린다.

내용이 넘치면 문장을 줄이거나 장을 나눈다. 본문을 작게 줄이는 일을 첫 해결책으로 삼지 않는다.
모든 장표에 목차·카드·사진을 넣을 필요는 없다.

## 두 번의 시각 검수

**HTML 단계:** contact sheet와 개별 장표를 실제로 연다.

1. 먼저 보이는 요소가 핵심 주장 또는 근거인가?
2. 근거가 설명을 줄여 주는가? 제목과 내용이 같은 결론을 가리키는가?
3. 한글 줄바꿈·정렬·대비·크기가 읽기에 충분한가?
4. 구도 반복 때문에 내용의 차이가 사라지지 않았는가?
5. 여백이 의도된 것인지, 구도가 미완성인지 판단했는가?

**PPT 단계:** 같은 장표의 HTML과 PowerPoint 렌더를 비교한다.

1. 글자·그림·표·단위·출처가 빠지지 않았는가?
2. 새 줄바꿈·겹침·폰트 대체로 전달 순서가 달라지지 않았는가?
3. 필수 텍스트와 도형이 편집 가능한가? 데이터 차트에 데이터 편집 기능이 있는가?
4. 원본·에셋·미리보기가 함께 있는가?

사용물을 보여주는 장표는 항목·행동 순서까지 읽혀야 한다. 종이처럼 생긴 빈 사각형만으로는 설명이 되지 않는다.
숫자와 단위가 서로 겹치면 하나의 텍스트 상자 안에서 크기를 달리하거나 실제 글자 폭에 맞춰 분리한다.
200px 이상의 큰 숫자는 행 높이를 충분히 확보한다. 도형을 겹칠 때는 뒤에 숨는 텍스트를 만들지 않는다.
표의 선·채움, 차트의 범주 순서·라벨은 PowerPoint에서 다시 확인한다.

안티앨리어싱의 작은 차이는 허용한다. 중요한 정보의 누락과 읽기 어려운 배치는 고친다.
렌더 자동화는 비교 이미지를 만들 뿐, 미적 품질을 증명하지 않는다.

## 스킬 개선 평가

예제 하나로 일반화를 선언하지 않는다. 성격이 다른 요청을 평가한다.

- CSV 기반 임원 보고: 숫자 근거·단위·강조·native chart 편집
- 제품 제안: 실제 화면의 비중·문제와 해결의 연결·이미지와 라벨 분리
- 한국어 교육: 긴 제목·단계도·적절한 장표 분리·독해 흐름

추가 디자인 지시가 없는 첫 결과와 수정 횟수를 기록한다. 같은 입력의 기존 Markdown 결과와 비교해
가독성·위계·구도·근거·편집성을 각각 판단한다. 개선·실패 사례를 함께 남기고 반복되는 실패만 지침에 반영한다.
