# 개인화 설계: 사람을 먼저 알고, 무엇을 만드는지 확인한 뒤 실행한다

> 이 스킬의 핵심이다. 덱을 만들기 전에 반드시 **사람(Profile)** 과 **산출물(Brief)** 을 확정하고, 둘을 합성해 **톤(Tone)** 을 결정한다.

## 1. 세 층 구조

```
Profile (사람, 한 번 만들고 계속 재사용)     ~/.pptkit/profile.yaml
   +
Brief   (이번 덱, 매번 새로 작성)            <작업폴더>/brief.yaml
   ↓  pptkit tone resolve
Tone    (렌더러가 쓰는 구체적인 값)          <작업폴더>/tone.yaml
   ↓
deck.md → pptkit build → .pptx
```

- Profile은 사용자 홈 폴더에 저장한다. 그래서 **어느 폴더, 어느 대화에서 실행하든 다시 묻지 않는다.** 이 점이 토큰 절감에도 직접 기여한다.
- Brief는 덱마다 다르다. 사용자의 요청 문장에서 최대한 추출하고, 비어 있는 핵심 항목만 질문한다.
- Tone은 사람이 쓰지 않는다. 스크립트가 Profile과 Brief를 합성해서 만든다. Claude는 결과 요약 한 줄만 읽는다.

## 2. Profile: 어떤 일을 하는 사람인가

| 항목 | 예시 | 톤에 미치는 영향 |
|---|---|---|
| `role` 직무 | 사업기획, 마케팅, 개발 리드, 연구원, 공무원, 강사 | 논리 구조(결론 먼저 / 배경 먼저), 전문용어 허용 수준 |
| `industry` 업종 | B2B SaaS, 금융, 제조, 공공, 교육, 의료 | 업종 관례(단위 표기, 색 금기, 보수성) |
| `org_culture` 보고 문화 | 두괄식 개조식, 서술형, 영문 혼용 | 문장 종결(`~함/~임` 개조식, `~합니다` 경어체, 구어체) |
| `audiences` 주 청중 | 임원, 팀 내부, 고객사, 투자자, 학생 | 밀도, 숫자 강조 방식 |
| `brand` 색·폰트 | 회사 대표색 HEX, 지정 폰트 (없으면 비움) | 팔레트의 기준색 |
| `density` 선호 밀도 | 여백 많은 발표형 ↔ 빽빽한 배포형 | 장당 글자 수 상한, 글자 크기 |
| `likes` / `dislikes` | "아이콘 남발 싫음", "표보다 차트 선호" | 금지 규칙과 우선 규칙 |
| `samples` 기존 자료 | 예전에 만든 .pptx 경로 | 스타일 자동 추출에 쓴다 (아래 4절) |

### 수집 방법 (토큰이 적게 드는 순서)

1. **기존 자료가 있으면 스크립트로 추출한다.** `pptkit style extract old.pptx`가 색 빈도, 폰트, 장당 글자 수, 개조식 비율, 제목 길이를 계산한다. Claude는 원본을 읽지 않고 약 100토큰짜리 요약만 본다.
2. **요청 문장에서 추론한다.** 예를 들어 "본부장 보고용"이라는 말에서 청중은 임원, 문화는 두괄식이라고 추론할 수 있다.
3. **남은 빈칸만 질문한다.** 첫 실행에서만 최대 5개를 묻는다. 각 질문에는 추천 기본값을 함께 제시해서 사용자는 고르기만 하면 된다.

## 3. Brief: 이번에 무엇을 만드는가

| 항목 | 질문 | 비고 |
|---|---|---|
| `purpose` | 보고, 제안, 교육, 피치·IR, 회고 중 무엇인가? | 장표 구성 순서가 달라진다 |
| `audience` | 이번 청중은 누구이고 무엇을 궁금해하는가? | Profile의 기본 청중을 덮어쓴다 |
| `ask` | 이 덱을 본 뒤 청중이 무엇을 결정하거나 행동해야 하는가? | 결론 장표와 요약 장표의 문장을 정한다 |
| `mode` | 발표용(말로 보충)인가, 배포용(읽기만 함)인가? | 밀도를 정하는 가장 큰 변수다 |
| `length` | 몇 장, 몇 분짜리인가? | 장표 수의 상한 |
| `materials` | 데이터 파일, 메모, 참고 링크 | 데이터는 `pptkit data`로 요약만 읽는다 |

`ask`와 `mode`는 품질에 가장 큰 영향을 준다. 요청 문장에 없으면 반드시 묻는다. 나머지는 추론하고, 추론한 값을 한 줄로 보여 준 뒤 진행한다.

## 4. 사전 조사 단계 (실행 전에 하는 일)

```
① Profile 확인     없으면 온보딩(기존 자료 추출 → 추론 → 질문 최대 5개)
② Brief 작성       요청 문장에서 추출하고, 빠진 핵심 항목만 질문 (최대 3개)
③ 도메인 조사      업종 관례 팩을 적용하고, 필요할 때만 content-research-writer로 근거를 조사
④ Tone 합성        pptkit tone resolve → 한 줄 요약
⑤ 톤 시안 2장      표지 + 대표 본문 1장을 먼저 만든다. 사용자가 확인한 뒤 전체를 생성한다
⑥ 전체 생성        deck.md → build → qa
```

⑤의 "톤 시안"이 개인화를 검증하는 장치다. 전체 덱을 만든 뒤 톤을 고치면 모든 장을 다시 생성해야 한다. 그래서 2장으로 먼저 확인하는 편이 토큰 면에서도 훨씬 싸다.

### 업종 관례 팩 (초안)

| 업종 | 관례 |
|---|---|
| 금융 | 단위를 억 원·조 원으로 표기하고, 증감은 %p로 쓴다. 빨강과 파랑의 의미가 국가마다 다르므로 상승·하락 색을 명시한다 |
| 공공 | 개조식 보고서체를 쓰고, 출처와 기준 시점을 반드시 표기한다. 장식은 최소화한다 |
| 스타트업 피치 | 한 장에 핵심 숫자 하나만 둔다. 문제 → 해결 → 시장 → 트랙션 → 팀 → 요청 순서를 따른다 |
| 컨설팅·기획 | 액션 타이틀(결론 문장)을 쓰고, 거버닝 메시지와 시사점 박스, 출처 각주를 둔다 |
| 교육 | 글자를 크게 쓰고, 한 장에 개념 하나만 둔다. 요약 장표를 반복한다 |

## 5. Tone: 렌더러가 쓰는 값

```yaml
# tone.yaml (pptkit tone resolve가 생성, 사람이 직접 고쳐도 된다)
base: consulting-navy          # 출발 프리셋
palette: {primary: "1F3A5F", accent: "E4572E", neutral: ["F4F5F7","8A94A6","2B2F36"]}
fonts: {title: "맑은 고딕", body: "맑은 고딕", number: "Arial"}
title_style: action-sentence   # action-sentence | noun-phrase
voice: gaejosik                # gaejosik(~함/~임) | formal(~합니다) | spoken
density: {max_bullets: 4, max_chars_per_bullet: 40, body_pt: 14}
numbers: {unit: "억 원", delta: "%p", thousands: true}
emphasis: one-accent           # 핵심값 하나만 강조색, 나머지 무채색
frame: kr-report               # 제목 / 거버닝 메시지 / 본문 / 시사점 / 출처
```

## 6. 평가 기준

개인화가 실제로 작동하는지는 다음으로 확인한다.

- 같은 데이터와 같은 요청을 **서로 다른 Profile 두 개**(예: 공공기관 사무관, 스타트업 대표)로 실행한다. 결과 덱의 문체, 밀도, 색, 장표 구성이 달라져야 한다.
- 두 번째 실행부터는 Profile 관련 질문이 0개여야 한다.
- 톤 시안 단계에서 사용자가 수정한 내용이 전체 덱에 반영돼야 한다.
